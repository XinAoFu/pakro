# SPEC — mise 原生包管理（项目/语言/包三方管理）

> 状态：待用户确认（2026-10-06 蒸馏自本会话需求讨论 + 《mise-包管理架构设计.md》）
> 上游文档：`/mise-包管理架构设计.md`（用户已批准的架构设计）

## 1. 背景与目的

mise（本仓库）已实现语言（工具）版本的精准安装、跨项目共享、按目录关联环境。但**包**（numpy、typescript 等库）的解析与安装全部委托给 pip/conda/uv/npm 等外部工具。本项目把包管理变成 mise 的原生能力：mise 自己解析依赖、自己下载校验、自己存储去重，全程不调用任何外部包管理器进程。

管理对象收敛为三方：**项目、语言、包**。

## 2. 术语

| 术语                | 定义                                                                                            |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| 语言（runtime）     | 一个语言的具体版本，如 python@3.10.14。沿用 mise 现有 `[tools]` 机制，本项目中不改动            |
| 包（package）       | 语言生态中的库及其传递依赖。本项目的核心新增对象                                                |
| 身份（identity）    | 包的唯一标识：`生态:名字@精确版本+运行时/平台/digest`。全局去重的依据                           |
| 仓库（store）       | 全局内容寻址存储目录，包按身份落盘，跨项目共享                                                  |
| 物化（materialize） | 在项目内生成符合语言查找规则的目录（venv 形状目录 / node_modules），内容为指向 store 的符号链接 |
| 解析器（resolver）  | 从版本约束求出互相兼容的具体版本集合的纯逻辑组件                                                |
| 锁文件              | `mise.lock`，v2 起记录完整依赖图（含传递依赖的精确版本与哈希）                                  |

## 3. 功能需求

- **FR-1 语言安装（现状保留）**：`mise install python@3.10.14` 行为与现有 mise 完全一致，零改动。
- **FR-2 原生包安装**：`mise install python@3.10.14+numpy@4.2.2` 一条命令装语言+包；同生态仅一个运行时时可省略绑定（`... numpy@4.2.2` 自动绑定）；多个运行时未显式绑定时报错并提示。安装全程不得调用 pip/uv/conda/npm 等任何外部包管理器进程。
- **FR-3 严格版本**：配置与命令中的版本一律精确（`3.10.14` 不写 `3.10`）。传递依赖由解析器解出具体版本后全部记入锁文件。顶层版本永不"猜最新"。
- **FR-4 多生态解析器**：解析器与生态无关，按生态注入版本语义。第一期实现 python（PyPI、仅 wheel）与 node（npm registry）；go（MVS）与 maven 为后续里程碑。
- **FR-5 平台自适应**：自动探测 os/CPU 架构/libc，据此选择安装产物（覆盖 numpy、CUDA 类按 python 版本与平台出不同产物的场景）。用户不手写平台。
- **FR-6 全局内容寻址仓库**：包按身份落盘 `store/`；相同身份跨项目只存一份；引用计数跟踪使用方；提供 `mise store ls` / `mise store gc`。
- **FR-7 环境物化**：python 每项目每运行时生成标准 venv 形状目录（site-packages 内为指向 store 的符号链接，bin 内入口接 shims），IDE 可直接选用该解释器；node 生成符号链接式 node_modules。生成的环境内默认不含 pip（逃生舱：把 pip 本身当包安装）。
- **FR-8 锁文件 v2**：记录整张解析图（名字、精确版本、digest、依赖边）。锁文件与配置一致时完全按锁安装（不重新求解）；配置变化时增量求解。
- **FR-9 配置格式**：新增 `[packages."python@3.10.14"]` 表（组键=运行时身份）。现有 `[tools]`/`[env]`/任务等所有既有语义零影响。
- **FR-10 项目对象**：`mise project init`（从零建：写配置，可选代码骨架）、`mise project attach`（先有代码：补写配置，绝不改动用户代码文件）、`mise project ls`、`mise project status`。项目不是数据库实体 = 目录树 + 树内 mise.toml + 全局索引（`projects.json`，仅服务于 ls，丢失可重建）。运行时关联机制沿用现有"从当前目录向上找配置"。
- **FR-11 安全**：注册表元数据声明的哈希写进锁文件，下载后强制核对，不符拒装；python 第一阶段仅收 wheel、npm 默认跳过生命周期脚本（不执行任何包的安装期代码）；产物只从官方注册表（可配镜像）下载。
- **FR-12 对照验证**：以 uv/pip-compile/npm 的解析结果为参照的差分测试 + 真实元数据快照语料库 + 离线性质测试，作为 CI 基础设施（参照工具仅测试期使用，运行时零依赖）。

## 4. 非功能需求

- **NFR-1 不做 Windows**：明确排除（M5 重评估）。物化统一用符号链接，无降级分支。
- **NFR-2 全 Rust**，加入现有 cargo workspace；复用 pubgrub、pep440_rs、pep508_rs、node-semver、petgraph 及仓库内既有 http/平台匹配/锁文件/信任检查能力。
- **NFR-3 分层可测**：resolver 为纯逻辑（无网络无磁盘，元数据注入）；index 只管拉取缓存；store 只管磁盘。同输入必同输出（确定性）。
- **NFR-4 向后兼容**：不修改任何现有 mise 行为；新能力全部在新表、新子命令、新 crate 中。
- **NFR-5 性能**：环境已就绪时 `mise install` 接近 no-op（查锁 + 建链接，不触网络）。

## 5. 范围外（本期不做）

- sdist/源码构建（明确报错说明，M5 再议）
- Windows 适配
- 非精确版本语法（范围约束作为用户可选项，M5 再议）
- conda 通道类非官方注册表源

## 6. 成功标准

- **M0**：`mise-store`（身份/路径/去重/引用计数/gc）与 `mise-resolver`（图类型/拓扑排序/确定性序列化）单测全绿；workspace clippy `-D warnings` 通过。
- **M1（python 端到端）**：`mise install python@3.10.14+numpy@4.2.2` 全程无 pip/uv 参与（进程级验证）；两个项目共享同一份磁盘上的 numpy（同一目录）；与 uv 在相同顶层约束下解出的版本集合一致（差分测试）；断网重装按锁文件成功（全部命中本机缓存/store）。
- **M2（node 端到端）**：同上对 npm registry；与 `npm install` 结果对照一致。
- **M3**：新人 clone 项目后 `mise install` 一条命令起完整环境（语言+包+入口命令可用）。
