# ADR-0001 总体架构：包管理四层划分与三个新 crate

mise 需要原生包管理能力（SPEC §1/§3）。决定：在现有 cargo workspace 中新增三个 crate——`mise-resolver`（纯逻辑依赖求解）、`mise-index`（注册表元数据拉取与缓存）、`mise-store`（内容寻址磁盘仓库）——加主 crate 内一个粘合模块 `src/packages/`（后端、物化、锁文件集成）。现有 toolset/install_layout/shims/hook_env/信任检查等能力原样复用，不改动。用户于 2026-10-06 会话中批准该设计（见《mise-包管理架构设计.md》），并明确：不做 Windows、全 Rust、能复用的开源实现直接复用。

## Considered Options

| 候选      | 形态                                        | 取舍                                                                                            |
| --------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| A（选定） | 三个独立 crate + 主 crate 粘合层            | 分层严格（纯逻辑/网络/磁盘分离），可独立单测、可差分测试；代价是跨 crate 接口要定义清楚         |
| B         | 全部做进主 crate `src/packages/` 一个模块树 | 少一层接口成本，但解析器会被网络与磁盘依赖污染，无法离线测试，与"对照验证"方法论冲突            |
| C         | fork uv 并内嵌为库                          | python 一家可以最快做对，但多生态（node/go/maven）立即失控，且违反"mise 亲手掌控解析"的项目目标 |

评估维度（用户会话中确认的优先级）：多生态覆盖 > 可测试性 > 与现有 mise 的兼容 > 短期速度。A 在前三维均最优。

## Consequences

- `mise-resolver` 不得依赖 reqwest/tokio/主 crate；`mise-index` 不得依赖主 crate；只有 `src/packages/` 可以引用全部三者（避免循环依赖，平台类型等公共类型定义在 mise-store）。
- 每个 crate 可单独 `cargo test`，差分测试可以只装 resolver。
