# Pakro 主架构文件与 Agent 规则

更新：2026-10-27（Asia/Shanghai）。本文件和 [PLAN](PLAN.md) 是现行入口；用户最新指令优先。

## 产品目标

Pakro 管理个人电脑中的语言、依赖包和项目关联。目标平台是 macOS 和 Linux；已取得的 Python 产品验收限本机 macOS arm64，其他平台不能凭源码存在宣称通过。开发顺序为 Python → Java → Node；Go 与独立 Rust 产品生态不在范围内，工程自身使用 Rust 或构建 Python 扩展需要 Rust 不改变此范围。

多个项目共用同一身份的实际 Python 和兼容包内容，各项目保留自己的依赖选择。项目目录保存源码和声明，不另放一整套 Python；必要的轻量链接、包布局和启动配置属于内部适配，不能变成用户必须创建、命名、激活的管理对象。

开发者手动维护项目配置。Pakro 读取并检查配置，缺项、冲突、不支持内容或与锁不一致时说明原因，不替用户编辑配置，不静默修改精确锁来使操作成功。

## 使用规则

1. 终端接入后，进入项目目录 → 读取配置与已有锁 → 查找已安装的语言和包 → 完整且匹配时选用。
2. 进入目录、查询路径、输出环境或找不到命令都不授权下载、升级或补装。缺什么就报告什么，由用户明确执行安装命令。
3. 显式安装可以获取必要依赖，已有完整且校验有效的内容直接复用；没有独立离线模式，已授权获取时网络失败如实报错。
4. 用户直接声明和安装请求必须使用完整精确版本；不自动把前缀、范围或 latest 补成一个版本。包作者的传递依赖范围由解析器处理，实际结果固定为精确制品。
5. 普通安装不自动回收。指定删除必须确认唯一目标，没有项目、依赖或在途操作保护才允许执行；未知状态不能当作无人使用。
6. 离开目录撤回终端选择，不等于解除持久项目关联。手动删配置项也不自动释放旧引用；显式更新成功提交新选择，或按精确项目ID执行forget，才解除对应旧关联。具体生命周期合同见PLAN。

## 架构与事实分工

| 部分 | 职责 |
| --- | --- |
| CLI | 解释命令、参数和用户意图，展示真实结果；不直接取得任意库文件的写删权限。 |
| install / uninstall / query 程序 | 分别协调安装、受控删除和只读查询，共用观察、上下文和提交内核。 |
| Python 适配层 | 解释声明、来源、依赖、构建和运行布局，复用现有求解、wheel、源码 worker 与运行时内核。 |
| 语言库 | 保存唯一实际语言内容和身份。 |
| 包库 | 保存包、构建产物及必要共享布局。 |
| 项目库 | 保存项目位置、当前已提交选择和真实依赖关系。 |
| 共享控制层 | 提供受控IO、内容校验、保护、发布、提交、恢复和删除许可。 |

四类事实各司其职：项目配置表示开发者意图；统一 `pakro.lock` 保存可移植精确结果；catalog 是本机项目选择和引用权威；manifest 记录实际内容及所有权。路径、临时凭证和运行租约不能冒充可移植身份，不另建第二套引用权威。

## 已有核心与修改边界

既有 P1/P2 保留：目录选用、显式精确 Python 安装、wheel 和限定 registry 纯 Python 源码包、项目关联查询、受引用保护的指定删除、统一精确锁、严格冷暖恢复，以及锁/catalog 受控提交和恢复。

- 首次受支持的项目安装可以按既有 P2 生成精确锁。已有锁按原图、来源和产物恢复，不重新求解、不静默改锁。
- 普通安装和查询遇到配置、目标、来源或产物与锁不符时拒绝，并保留原选择。手动修改配置后，可按PLAN明确执行`install --update-lock`准备新结果并共同提交；旧兼容版本/来源/制品优先，损坏或不支持格式的旧锁仍拒绝，不通过删锁或伪造无锁会话绕过。
- 锁/catalog 采用同一持久 journal 协调，catalog 作为逻辑提交点；不把跨文件系统多次 rename 宣称为物理原子。
- 查询遇到未完成提交，只读上次完整事实或报告待恢复，不自动恢复。显式安装中的既有中断恢复仍须核对原输入、外部编辑和后续 revision；它不能扩大成配置修正或任意内容修复。
- 原始源码、精确构建输入和实际输出分别核验。构建请求身份不等于输出摘要，重建结果变化不得悄悄更新锁。
- 保持项目 → 对象 → catalog 的锁顺序和实际保护。新增关联、删除及在途恢复必须使用共同事实，未知引用不能按零处理。
- 优化不得削弱完整内容/manifest/来源校验，不用提高超时或文件句柄额度代替结构改进，不擅自加入跨操作摘要缓存。
- 既有四项 pyc 恢复只是固定原归档、原实例及其余内容严格不变的特例，不推广为通用 repair/force。

## 最新范围调整

| 项目 | 现行决定 |
| --- | --- |
| 自动编辑配置 | 取消。开发者手动维护，Pakro 校验并合理报错；不实施 use/add/remove/upgrade 自动声明编辑事务。 |
| P3 | 原自动声明编辑范围撤回。显式更新锁、最后根释放、精确ID forget、先新目录登记再forget旧ID的生命周期合同已由PLAN确定；实施状态只见PLAN。 |
| P5 | 整体取消，不扩建项目 Git/local、直接URL、私有registry等完整来源阶段；现有正常语言和包的来源获取保留。解释器发行包托管在 GitHub，不等于克隆或下载项目源码。 |
| P7 editable | 已取消。不实现本地活源码绑定、editable安装及其生命周期，也不作为Python完成要求。 |
| P8 Conda | Pakro 直接读取 Conda 包源、解析元数据和包格式、求解并安装受管内容。不得安装、调用或嵌入 conda/mamba 管理器；可复用底层协议、求解和解包库。 |
| 非核心旧功能 | 本轮直接删除已排除的旧功能，不保留兼容入口；必要目录接入及现有 Python P1/P2 内核继续保留。实际完成范围见 PLAN。 |
| 文档 | 实施状态只维护同目录 PLAN；本文件沿用当前位置规定架构，根 README 提供简短使用说明，AGENTS 提供入口，不再累积历史快照。 |

`install-into` 已取消。系统初始化、dotfiles、后台服务、远程任务等非核心产品功能不恢复；删除时不得误删核心安装、终端选择、沙箱及工程验证实际依赖。缓存、诊断、环境信息和自身维护等已保留辅助职责以实际支持范围为准，不把名称相似当作重复功能。

## 后续完成要求

剩余工作按 [PLAN](PLAN.md) 管理：依次实现已确定的必要锁/关联生命周期、显式回收、保留的构建能力和Conda直接管理，最后完成Python平台与真实项目验收。P5、P7均取消，不沿用旧R/F/S任务清单自动扩大范围。

每个保留来源、构建后端或对象都要接通安装、锁、查询、引用和受控删除，不能只做到下载。Java/Node的新共享实现须等Python阶段完成后按顺序进入；IDE及外部直接解释器的完整运行生命周期另列后置，路径查询不代表持有运行租约。

## P4 删除与续行约束

- 精确卸载和prune共用实际删除内核；预览、图视图和候选ID均为描述，不授予删除权限。当前全部项目槽与未完成操作提供根，实际包/语言/布局提供边，退休记录不成为永久根；未知出边或损坏权威导致视图不完整，不能按空引用继续。
- 操作记录放在现有受控项目库journal，固定原候选、库/锁/目录身份及原manifest；逐对象不可变清单与短进度分开保存，避免每删一个文件就重写完整大清单。对象库的pending-deletion claim在同库catalog保护下阻止同身份发布，不成为第二套引用数据库。记录及claim先持久化，之后才撤Ready。
- 每个工作组按跨库固定顺序非阻塞取得全部实际EX，任一忙碌即释放整组；取得后重新核当前根、外部保留对象及完整内容。按引用者先于依赖处理，无根环整组删除；暂留或失败对象的依赖闭包保留。组容量显式受限，不能拆环绕过。
- syscall前记录意图，完成及父目录fsync后记录进度。续行只接受原身份；仅当前已记录pending的动作允许目标已经不存在。剩余树有陌生条目、目录替换或内容变化时拒绝，不递归清空。只有实际持有的原保护及受控记录与当前物理状态共同核实后才能恢复，不能由反序列化DTO直接造删除许可。
- 布局撤Ready前保存其完整清单并纳入物理回收；旧无manifest目录没有可信清单，只报告未知。物理清理后才CAS清退休索引，保留稳定锁、选择版本及防旧进程复活记录。prune续行不加入新候选；`--resume --dry-run`只读展示原操作，不推进删除。

## P6 构建和布局边界

- 原recipe1和no-fork worker保持原驱动字节、请求配置及指纹语义；新编译能力必须用独立driver/worker与版本化构建记录，工具链、SDK、规范化参数及监督策略共同进入可移植请求身份。本机绝对路径、FD、inode只用于本机绑定。
- 原生编译配方只有在实际执行身份、生成程序登记、子进程监督和父进程退出清理均取得真实证据后才开放。2026-10-26用户已明确同意本轮覆盖正常公开后端及取消、超时、Pakro意外退出；暂不为恶意脚本主动脱离会话、攻击监督进程扩建大型防御体系。Linux可以用实际PID命名空间收束任务；macOS可以用独立监督进程管理整个构建会话，必须覆盖Ninja正常建立子进程组，不能只杀最外层进程组。不因后端需要派生就直接取消现有文件、网络隔离或生成程序登记。
- 生产原生工作区在监督进程成功启动后、首次等待前移交清理责任；源码树、嵌套构建环境和语言准备对象不得在future被丢弃时抢先chmod或删除。只有Finish得到成功退出确认才归还父侧清理。Linux独立watcher以subreaper实际收完命名空间init及收养子进程，只有ECHILD确认清空；macOS枚举进程失败不能当作空会话。停止未确认时保留私有目录并报告，不用固定sleep假定清理完成。
- 受控Python子进程继承本次固定构建依赖，禁用用户site并保持执行登记和文件/网络隔离；普通代码、模块、脚本和stdin入口保留原调用对当前目录及-I/-P的搜索选择。该适配限既定构建入口，不扩建通用进程虚拟化。
- Linux原生布局用实际reflink或核验独立复制的方法区分新配方/清单，旧配方保持可读。只有明确不支持/Cross-device等能力错误允许受控丢弃未发布输出后全图降级；I/O、权限、空间或来源变化不降级，不用hardlink，不复制整套Python。
- 源码CPython的系统运行库策略允许macOS系统库及Linux发行版常规系统ABI；不接通额外共享库管理时，拒绝依赖SDK、Homebrew或临时目录动态库的产物。检查本次二进制依赖并在不授予构建SDK读取、不继承动态库搜索环境的条件下验证必要标准库；记录实际运行库及可选组件结果，不固定整个操作系统或每次查询重探针。静态开发库可作为明确构建输入。
- 源码CPython默认运行时配方明确不构建或安装CPython自身回归套件和测试扩展（官方`--disable-test-modules`），普通标准库、`unittest`/`unittest.mock`/`doctest`及七项必要功能保留。此为版本化产物配置，参与请求和输出身份并在查询中展示；旧含测试套件配方按旧记录读取，不按新配置解释，也不影响包构建的旧recipe1/no-fork。不能称为透明性能修复或借此宣称旧大对象回收性能已通过。
- 有界raw源码树与Python包声明解析分层。sdist新增ZIP必须同时接通registry身份、锁和解包；官方CPython的tar.xz仅为raw来源入口，不能伪装已安装PBS或绕过语言构建/验证发布协议。所有解码器保留展开、条目、路径、deadline及完整尾部核验，XZ另有硬内存上限。

## Agent 工作规则

- 整个项目禁用 `dev-flow` skill，不加载、不调用、不套用固定阶段门或TDD/审查循环。
- 只执行用户当前授权。旧日志和历史授权不恢复；Git提交和推送分别需要用户当次明确指令，不操作用户实际库和项目数据。
- 本轮允许按最新范围删除非核心旧代码，保留核心Python P1/P2；不能把原有验收当成本轮修改后的通过结果。
- 每组Agent编译、检查、测试或脚本共同墙钟上限600秒，保存真实输出；超时停止自己启动的进程并报告，不拆分或重试绕过上限。
- 自动多进程运行器继续禁用；长验证由用户终端执行。交付命令先用大白话说明“现在要测试什么”，再给可直接复制的完整命令及必要输入。
- 只依据实际退出码、用例数和结果判断，零测试、全ignored、只有编译成功不算行为验收；未变化且已通过的检查不无故重复。
- 复用同一target和构建配置；不清用户库或有效输入。`target/`中的原始验收证据不入Git，清理前保留仍需的日志和摘要。
- 进度只维护一份PLAN，不再创建HANDOFF、TESTS、FILES、历史归档或开发日志。必要状态直接更新PLAN，详细执行输出保留在target。
